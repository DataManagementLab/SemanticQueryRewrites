Join simplification shortcuts
When a joined table does NOT appear in the SELECT list and serves only as a filter or existence check, it may be possible to eliminate the join entirely using world knowledge. This is a powerful optimization because removing a join reduces the number of tables the optimizer must consider, shrinks intermediate result sets, and avoids unnecessary I/O. Look for these patterns:

- FK-value substitution (lookup tables): Small lookup tables like info_type, kind_type, role_type, company_type, link_type, and comp_cast_type are frequently joined only to filter by a human-readable text value (e.g., info_type.info = 'rating'). If you know the numeric ID for that text value, you can add the ID as a direct filter on the FK column of the fact table and mark the lookup table for elimination. For example, if the query joins info_type and filters info_type.info = 'genres' and you know info_type.id = 3 for 'genres', then add movie_info.info_type_id = 3 and eliminate info_type from the join.

- FK-value substitution (dimension tables): Larger dimension tables like keyword, company_name, or name may also be joined only to filter by a specific value that does not appear in SELECT. If you know the entity's primary key ID, you can substitute a direct FK filter and eliminate the dimension table join.

- Guaranteed-existence elimination: A table is joined purely as an existence check (semi-join pattern), but world knowledge guarantees that every row from the driving table already has a matching partner. For example, if every movie of kind_id = 1 is guaranteed to have at least one entry in movie_companies, and movie_companies has no additional filters and does not appear in SELECT, then the join to movie_companies is a no-op and can be dropped.

- Redundant filter join: A table is joined to apply a filter, but another predicate on the fact table already achieves the same filtering effect. For example, if cast_info.role_id = 1 is already present (from another rule or the query itself), then joining role_type solely to filter role_type.role = 'actor' is redundant and role_type can be eliminated.

When you identify a join simplification opportunity, produce a rule of type "join_elimination" (see format below). Be conservative: only eliminate a join when you are certain the table does not contribute columns to the result and its filtering effect is fully captured by the implied predicates.

Rule format
A rule has a type (either "filter" or "join_elimination"), one or multiple conditions (connected solely by AND or OR in an upper-level statement) that must be part of the SQL (so should be fulfilled in the current SQL), and implies one or more additional filters that can be applied and are likely to speed up the query.

For "filter" rules (adding predicates only): the rule adds the implied predicates to the WHERE clause.
For "join_elimination" rules (removing a join): the rule adds the implied predicates AND removes the specified tables from the query. The "eliminates" field lists the base table names to remove. A table may only be eliminated if it does not appear in SELECT, GROUP BY, ORDER BY, or HAVING, and all its filtering conditions are captured by the requires/implies predicates.

Do not invent any other fields in a rule set. Use exactly the operators that are used in the current SQL query for the conditions. The value of a condition or implied answer can only be of primitive datatypes or lists. You can not run subqueries with that. You can not put a value of another column there (join like). Be aware that your rules must contain all necessary preconditions for applying a rule. This is very important. If in doubt, better include more predicates to make sure the rule is not applied in cases where it is not valid. It must work with arbitrary SQL statements as long as the conditions are fulfilled. Stick exactly to these rules and this format.

CRITICAL — what goes in "requires":
- "requires" must contain ONLY filter predicates that literally appear in the query's WHERE clause — comparisons of a column against a literal value (string, number, or list).
- Do NOT include join conditions (column = column comparisons like role_type.id = cast_info.role_id) in requires. Join relationships are handled automatically by the engine and must not appear in conditions.
- Do NOT include data facts you are discovering. For example, if you know that role_type.id = 1 corresponds to 'actor', do NOT put role_type.id = 1 in requires — that is what the rule computes via implies, not a precondition from the query.
- Always use base table names in column references (e.g., role_type.role), not query aliases (e.g., rt.role).

Example 2 (join_elimination rule — FK-value substitution removing a lookup table):
Scenario: a query contains "WHERE ... AND role_type.role = 'actor' ... AND role_type.id = cast_info.role_id ...". The only filter predicate on role_type is role_type.role = 'actor'. You know that the IMDb ID for 'actor' is 1, so you can add cast_info.role_id = 1 and eliminate the role_type table.
{{
    "id": "IMDB_JE_ROLE_ACTOR",
    "type": "join_elimination",
    "requires": {{
        "op": "AND",
        "conditions": [
            {{
                "column": "role_type.role",
                "op": "=",
                "value": "actor"
            }}
        ]
    }},
    "implies": [
        {{
            "column": "cast_info.role_id",
            "op": "=",
            "value": 1
        }}
    ],
    "eliminates": ["role_type"]
}}
Note: requires contains ONLY the filter predicate role_type.role = 'actor' from the WHERE clause. It does NOT include the join condition role_type.id = cast_info.role_id (that is a join, not a filter) and does NOT include role_type.id = 1 (that is a data fact, not a query predicate). The FK value 1 appears only in implies.

Common mistake to AVOID in join_elimination rules:
Do NOT put join conditions or FK IDs in requires. This is WRONG:
"requires": {{"conditions": [
    {{"column": "role_type.role", "op": "=", "value": "actor"}},
    {{"column": "role_type.id", "op": "=", "value": "cast_info.role_id"}}  <-- WRONG: this is a join condition, not a filter
]}}
Also WRONG:
"requires": {{"conditions": [
    {{"column": "role_type.role", "op": "=", "value": "actor"}},
    {{"column": "role_type.id", "op": "=", "value": 1}}  <-- WRONG: this is a data fact you discovered, not a predicate in the query
]}}
The correct requires contains only: {{"column": "role_type.role", "op": "=", "value": "actor"}}
