IMDb-specific, world-knowledge-driven shortcuts you should consider when applicable
- Prefer primary entities over aliases: avoid aka_title and aka_name unless alternates are explicitly needed; most queries can use title and name only.
- Production year sanity: Think about which time period the queries intention addresses. You may be able to reduce the query time by filtering on the movie time.
- Kind narrowing: Which kind of movie/... does the query implicitely address?
- Companies: when looking for producers or distributors, filter company_type.kind and avoid broad company joins.
- Links: depending on the intent, restrict link_type.link to certain values
- Episodes: if series/episode details are not central, avoid episode_of_id/season_nr/episode_nr joins; TV episodes can be voluminous.
- Well-known entities: When filtering for well-known entities that you know (actors, directors, producers, specific movies, franchises, studios, genres, countries), take into account your knowledge about such entities to prune tables with eg. filters. Think about what you know about the entity and what constraints that implies on the joined tables.
- Think of more and other filters that can be applied, depending on the queries tables and filters.

Join-aware optimization shortcuts
- FK-value substitution: When the query joins a small lookup table (kind_type, info_type, company_type, role_type, link_type, comp_cast_type) solely to filter by a text value, and you know the corresponding numeric ID for that text value, add the numeric ID as a direct filter on the FK column of the main table. For example: if the query filters kind_type.kind = 'movie' and you know that this corresponds to kind_type.id = 1, then add title.kind_id = 1 as an implied filter. This allows the optimizer to filter the main table directly on the FK column before joining, which is much faster.
- Cross-table constraint propagation: If filtering table A constrains what can appear in joined table B (via world knowledge), add that constraint directly to B. Think about what each existing filter implies about ALL joined tables, not just the table it directly filters. For example, if the query filters for a specific person who you know is an actor, add a role filter on cast_info or role_type.
- Bound tightening: If the combination of existing filters implies a tighter range than what the query specifies, add the tighter bound. For example, if other filters imply all matching movies must be from after 2000, add production_year > 2000 even if the query only says production_year > 1950.
- Join cost awareness: Consider which joins are most expensive (large tables: cast_info ~36M rows, movie_info ~15M rows, movie_companies ~2.6M rows, movie_keyword ~4.5M rows, person_info ~3M rows). Any filter you can add to EITHER side of an expensive join reduces intermediate result sizes dramatically. Think about what world knowledge tells you about the rows that will survive each join.
